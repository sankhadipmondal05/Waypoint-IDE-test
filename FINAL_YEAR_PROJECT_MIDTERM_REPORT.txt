3. One-Paragraph Executive Summary:
   Waypoint IDE is an offline-first, student-focused desktop Integrated Development Environment engineered specifically for beginners learning C, C++, Java, and Python. Developed using a hybrid desktop architecture combining a React 19 / TypeScript presentation layer with a high-performance Tauri v2 / Rust native core, Waypoint intentionally eliminates the cognitive friction, complex configuration, and visual clutter characteristic of professional IDEs like Visual Studio Code. The platform integrates Microsoft Monaco Editor, native system compiler toolchains (MinGW GCC/G++, OpenJDK, Python 3), an interactive terminal emulator with stdin piping, and a local on-device AI mentor powered by Ollama. Anchored by the pedagogical philosophy "Write -> Run -> Understand -> Review -> Improve", Waypoint enforces strict educational boundaries: AI assistance is explicit and on-demand, never writing code autonomously or interrupting the student. When execution fails, deterministic error parsing couples with local language models to deliver educational explanations; when explicitly requested, the system performs single-issue, progressive code reviews contextualized by student-authored problem statements, displaying minimal red/green logic diffs without cloud connectivity or recurring subscription costs.

4. The Core Problem Being Addressed:
   First- and second-year undergraduate computer science students encounter severe impediments when learning programming: steep toolchain installation curves, unintelligible compiler diagnostics (e.g., GCC linker failures, cryptic template errors), and confusing multi-file configurations in enterprise IDEs. Simultaneously, the proliferation of cloud-based AI code generators (e.g., GitHub Copilot, ChatGPT) has created a pedagogical trap where students bypass analytical problem-solving by copying generated code wholesale. Waypoint addresses this by providing a lightweight, zero-configuration local IDE that executes code deterministically and restricts AI to an on-demand, educational mentoring role that explains errors and suggests one targeted optimization at a time.

5. Intended Users and Stakeholders:
   - Primary Users:
     * B.Tech / B.E. / BCA / B.Sc. Computer Science and Engineering students in foundational programming laboratory courses.
     * High school and junior college students starting with basic algorithmic problem solving.
     * Novice programmers practicing Data Structures and Algorithms (DSA) problems.
   - Secondary Stakeholders:
     * University Laboratory Instructors and Teaching Assistants seeking a standardized, cheat-resistant lab environment.
     * College IT Administrators managing offline lab computers with restricted internet privileges and heterogeneous hardware specifications (4 GB to 8 GB RAM).

6. Motivation and Practical Relevance:
   - University Computer Labs in developing regions frequently operate behind strict institutional firewalls or experience intermittent internet connectivity. Cloud-tethered IDEs (Replit) or cloud-hosted LLM APIs (OpenAI API) are economically unviable and technically unreliable in such environments.
   - Commercial IDEs (VS Code, CLion, Eclipse) have memory footprints frequently exceeding 1 GB, causing sluggishness on legacy institutional hardware. Waypoint utilizes Tauri's lightweight Webview2 footprint (~35-60 MB idle UI memory) combined with quantized small language models (SLMs <= 3B parameters) running locally on CPU or low-end GPU hardware.
   - Pedagogical integrity demands that students retain cognitive responsibility for their syntax and logic. An IDE that restricts AI to post-execution explanation and bounded review protects the educational learning curve.

SECTION B — PROBLEM STATEMENT
================================================================================

1. The Specific Problem Being Addressed:
   Beginner programmers and engineering undergraduates face four major structural hurdles in standard university lab curricula:
   a) Excessive Toolchain Setup Friction: Novice students lose hours struggling with PATH environment variables, MinGW installation directories, JDK CLASSPATH configurations, and IDE compiler flags before writing a single line of code.
   b) Cryptic Compiler & Runtime Diagnostics: Native compiler error outputs from GCC, G++, Javac, or Python contain internal system paths, linker references (`undefined reference to WinMain`), and template noise that intimidate beginners rather than guiding them toward syntax resolution.
   c) Cognitive Overload in Modern IDEs: Enterprise IDEs (Visual Studio Code, IntelliJ IDEA, Eclipse) are built for enterprise software engineering. They overwhelm beginners with thousands of settings, complex configuration files (`tasks.json`, `launch.json`, `.vscode`), extension marketplaces, and multi-pane clutter.
   d) The AI Hallucination & Passive-Learning Trap: Modern cloud generative AI tools either generate entire blocks of unverified code (preventing students from understanding fundamentals) or produce hallucinated syntax that does not match local compiler realities.

2. Existing Approaches and Systems:
   - Category 1: Heavy Enterprise IDEs (Visual Studio Code, JetBrains CLion, Eclipse, IntelliJ).
   - Category 2: Outdated Educational IDEs (Turbo C++, Dev-C++, Code::Blocks, IDLE).
   - Category 3: Cloud Web IDEs (Replit, Programiz, LeetCode, HackerRank).
   - Category 4: Cloud AI Coding Assistants (GitHub Copilot, Cursor, ChatGPT).

3. Known Limitations of Existing Approaches:
   - VS Code / CLion: Require extensive configuration; memory-intensive (often > 800 MB RAM); extensions frequently conflict; requires internet for most diagnostic extensions.
   - Turbo C++ / Dev-C++: Turbo C++ relies on 16-bit DOSBox emulation, teaching obsolete non-standard C++ (e.g., `<iostream.h>`, `void main()`, `conio.h`) that fails on modern operating systems and industry standards. Dev-C++ lacks modern language features, auto-formatting, and intelligent error explanation.
   - Replit / Online Compilers: Inoperable without uninterrupted high-bandwidth internet; introduce latency on university networks; cannot interact with native desktop peripherals or files directly.
   - GitHub Copilot / Cursor: Always-on autocomplete interrupts student thought processes; ghost-text encourages guessing; cloud subscription cost ($10-$20/month/student) is prohibitive for public institutions; student source code is transmitted to external cloud servers.

4. Why the Proposed Solution (Waypoint IDE) is Useful:
   - Built specifically around the modern C++17, C11, Java 17+, and Python 3 standards.
   - Utilizes a lightweight native desktop wrapper (Tauri + Rust) consuming minimal system resources.
   - Keeps deterministic execution strictly separated from AI heuristics: code is compiled and executed by real system compilers, not simulated by an LLM.
   - Provides a five-step automated Setup Wizard that scans system PATH, detects toolchains, installs missing compilers via Windows Package Manager (`winget`), and manages local AI models.
   - Implements a single-issue, bounded code review mechanism that only fires on explicit student demand and refuses to rewrite entire files.
   - Features deterministic path sanitization that strips confusing internal compiler paths and translates cryptic linker errors into clear pedagogical advice.

5. Research and Implementation Gap:
   Current academic literature and commercial tooling exhibit a marked gap: there is an absence of unified, offline-first educational desktop environments that pair deterministic local compiler toolchains with privacy-preserving, on-device Small Language Models (SLMs) governed by strict pedagogical interaction constraints (no autocomplete, on-demand activation, mandatory problem context, and single-finding diffs).

6. Facts Requiring External Confirmation / User Input:
   - Quantitative baseline data comparing the error-resolution speed of students using Waypoint versus students using standard terminal/VS Code.
   - Formal survey feedback from university faculty regarding institutional adoption constraints.
   - Empirical memory and power consumption benchmarks across specific lab PC hardware configurations (e.g., Intel 4th Gen Core i3 with 4GB RAM vs Intel 12th Gen Core i5 with 16GB RAM).

SECTION C — OBJECTIVES AND SCOPE
================================================================================

1. Main Project Objective:
   To design, architect, and implement a lightweight, distraction-free, offline-first desktop Integrated Development Environment (Waypoint IDE) that streamlines local compilation for C, C++, Java, and Python, while integrating on-device AI mentoring to explain errors and provide progressive, pedagogical code improvements without compromising student cognitive ownership.

2. Specific Technical Objectives:
   - Objective 1 (Desktop Shell): Build a responsive desktop application shell using Tauri v2 and React 19/TypeScript adhering to an academic "Sand / Editorial" visual design language implemented exclusively in Vanilla CSS.
   - Objective 2 (File Management): Implement an in-memory and persistent workspace tree supporting file/folder creation, deletion with safety confirmation, inline renaming, and drag-and-drop hierarchy reorganization.
   - Objective 3 (Code Editing): Integrate the Microsoft Monaco Editor with customized Sand Light and Dark themes, dynamic zoom levels, unsaved state tracking, and line error highlighting.
   - Objective 4 (Process Execution): Develop a Rust-based native execution pipeline capable of invoking GCC, G++, OpenJDK (javac/java), and Python 3 with piped stdin, process timing, and exit code capture.
   - Objective 5 (Diagnostic Sanitization): Engineer an error sanitization pipeline that parses compiler stderr streams (GCC, Javac, Python tracebacks), extracts file/line/column coordinates, strips internal system paths, and translates obscure linker faults into actionable advice.
   - Objective 6 (Interactive Terminal): Embed an interactive terminal emulator supporting direct shell command execution via native child processes and an interactive stdin prompt for programs requiring user input (`scanf`, `cin`, `input()`).
   - Objective 7 (Local AI Orchestration): Implement direct integration with the Ollama local inference engine via raw TCP and HTTP APIs, supporting live model status scanning, automated daemon initialization, background model pulling with byte progress streaming, and latency verification.
   - Objective 8 (Constrained Pedagogical Review): Build an on-demand code review engine that enforces single-issue, targeted optimization diffs contextualized by user-supplied problem statements, backed by a deterministic heuristic/regex rule engine fallback for 100% offline reliability.
   - Objective 9 (Lab Deployment Packaging): Package the application into a standalone Windows installer using Inno Setup that bundles prerequisites and registers system environment paths.

3. Core Features and Modules:
   - Module 01: TopBar & Workspace Navigation Header (Run, Review, Layout Toggles, Theme Switch, File Problem Statement Input, Update Badge).
   - Module 02: Project Explorer & Virtual File Tree (Hierarchy tree, Drag-and-Drop, New File/Folder modals, Confirm Delete modal).
   - Module 03: Monaco Editor Pane & Tab Manager (Multi-tab management, Sand Editorial themes, dynamic font scaling, error line glyphs).
   - Module 04: Native Execution Manager (`compile_and_run_file` in Rust, language detection, compiler invocation, process timing).
   - Module 05: Output Console & Stdin Prompt Handler (Execution banners, stdout display, interactive prompt extraction, execution time in ms).
   - Module 06: Integrated Terminal Emulator (`run_terminal_command` in Rust, command history navigation with Arrow Up/Down, built-in commands: run, ls, cat, help, clear).
   - Module 07: Setup & Environment Wizard (`SetupWizardModal`, 5-step modal, toolchain scanner, winget installer trigger, model downloader).
   - Module 08: Local AI & Ollama Service (`OllamaService`, TCP stream health checks, HTTP `/api/pull` streaming, `/api/generate` verification, daemon lifecycle management).
   - Module 09: AI Review & Heuristic Engine (`ReviewService` and `AstAnalysisService`, problem statement injection, single-issue prompt formatting, deterministic rule catalog).
   - Module 10: Production Installer Script (`setup.iss`, Inno Setup 6.7+ configuration, automated PATH registration).

4. Functional Requirements (Identifiable from Codebase):
   - FR-01: System must support source files in C (`.c`), C++ (`.cpp`), Java (`.java`), Python (`.py`), Markdown (`.md`), and JSON (`.json`).
   - FR-02: User must be able to create, rename, delete, and reorganize files and folders via an intuitive Project Explorer.
   - FR-03: Editor must provide syntax highlighting, bracket matching, line numbers, and Ctrl+S persistence.
   - FR-04: Run command must detect file extension and invoke appropriate local compiler/runtime without manual configuration.
   - FR-05: Execution engine must capture stdout, stderr, execution duration, and exit status code.
   - FR-06: Programs requiring console input (`scanf`, `cin >>`, `input()`) must present an interactive input interface and pipe values into process stdin.
   - FR-07: When compiler errors occur, editor must highlight offending line and display a sanitized diagnostic message with plain-language explanation.
   - FR-08: User must enter a Problem Statement before requesting an AI code review to ensure contextualized analysis.
   - FR-09: Code review must return exactly one high-priority finding with original code, suggested replacement code, and impact explanation, or declare the code optimal.
   - FR-10: Application must detect whether Ollama is active on localhost:11434 and automatically attempt to launch the background daemon if missing.

5. Non-Functional Requirements:
   - NFR-01 (Offline-First): All editing, saving, compilation, execution, error parsing, and local AI reviews must function without an internet connection once initial setup is complete.
   - NFR-02 (Performance & Lightweight Footprint): Editor startup time must remain under 3 seconds; execution initiation overhead must not exceed 100 ms; UI bundle size must remain compact.
   - NFR-03 (Data Privacy): Student code and problem statements must never be transmitted to external third-party cloud servers; all AI inference must execute on local hardware.
   - NFR-04 (Pedagogical Safety): AI must not provide full code replacements, ghost-text autocomplete, or unsolicited interruptions while coding.
   - NFR-05 (Aesthetic Restraint): UI must adhere strictly to the Sand / Editorial design system using Vanilla CSS, avoiding neon themes, cluttered toolbars, and chatbot avatars.
   - NFR-06 (Portability): Application must be distributable as a self-contained Windows executable and installer.

6. Scope Boundaries:
   - In-Scope:
     * Desktop single-window IDE layout.
     * C, C++, Java, and Python local compilation and execution.
     * Monaco Editor integration with custom themes.
     * Interactive stdin handling.
     * Sanitized error diagnostics with line mapping.
     * Local Ollama SLM integration and fallback heuristic rules.
     * Single-issue progressive code review with targeted diffs.
     * 5-step Setup Wizard and Windows Inno Setup installer.
   - Out-of-Scope (Explicit Non-Goals as defined in PRD):
     * Replacement for enterprise IDEs (no extension marketplace, no multi-root workspaces).
     * Autonomous AI coding agents or always-on ghost-text autocomplete.
     * Full Git GUI client (commit graph, merge conflict resolver, branch visualizer).
     * Cloud collaboration, pair programming, or telemetric classroom monitoring.
     * Multi-language debugging engine (no GDB/LLDB interactive breakpoint stepping in current build).

7. Intended Final Deliverables:
   - Production desktop application installer (`Waypoint-IDE-Setup-0.1.0.exe`).
   - Standalone compiled binary (`waypoint-ide.exe`).
   - Complete TypeScript/Rust source codebase with modular architectural separation.
   - Comprehensive technical documentation suite (`PRD.md`, `ARCHITECTURE.md`, `DESIGN.md`, `MEMORY.md`, `PHASES.md`, `RULES.md`).
   - Academic B.Tech project report and slide presentation deck.

SECTION E — SYSTEM ARCHITECTURE
================================================================================

1. Major System Components:
   - Layer 1: Presentation & UI Tier (React 19 + TypeScript + Vanilla CSS).
   - Layer 2: IPC Bridge (Tauri v2 Inter-Process Communication Channel).
   - Layer 3: Native Core Engine (Rust `app_lib` crate).
   - Layer 4: Execution & Toolchain Subsystem (OS Child Process Spawner).
   - Layer 5: Local AI Subsystem (Ollama Daemon via Localhost HTTP/TCP).
   - Layer 6: Persistence & File Storage Subsystem (LocalStorage + OS Temp Runner).

2. Responsibilities of Each Component:
   - React UI Layer: Manages application layout, resizable panels, Monaco Editor state, tab bar, project explorer virtual tree, terminal UI, review console diff rendering, and modal dialogs.
   - Tauri IPC Bridge: Serializes frontend requests into typed JSON payloads and dispatches them across the desktop security boundary into Rust command handlers.
   - Rust Core (`src-tauri/src/lib.rs`): Executes child processes without spawning secondary console windows (`CREATE_NO_WINDOW = 0x08000000`), performs TCP socket polling on port 11434 to verify Ollama daemon health, streams file contents to temporary disk buffers, captures stdout/stderr, and terminates orphaned background processes upon window close.
   - Toolchain Subsystem: Locates native system binaries (`gcc`, `g++`, `javac`, `java`, `python`, `cmd.exe`) in system PATH, compiles source files, measures execution duration, and enforces unbuffered real-time stdout streaming (`python -u`).
   - Local AI Subsystem: Communicates with Ollama running at `http://localhost:11434`, pulls quantized GGUF models directly, streams layer download progress, and issues constrained JSON prompts to generate single-issue reviews.

3. Inter-Component Communication Protocol:
   - Frontend to Rust: Explicit Tauri Commands invoked via `@tauri-apps/api/core`:
     * `compile_and_run_file`: Transmits `{ fileName, content, stdinInput }` -> Returns `CommandOutput`.
     * `run_terminal_command`: Transmits `{ command, cwd }` -> Returns `CommandOutput`.
     * `scan_system_toolchains`: Dispatches parallel version queries -> Returns `Vec<ToolchainScanResult>`.
     * `ensure_ollama_running`: Checks port 11434 -> Spawns background `ollama serve` if disconnected.
     * `kill_ollama_daemon`: Issues `taskkill /F /IM ollama.exe /T` on Windows or `pkill` on Unix.
     * `get_ollama_status`: Raw TCP socket request to `GET /api/tags` -> Returns `OllamaModelStatus`.
     * `trigger_ollama_pull`: Spawns async thread executing `ollama pull <model>`.
   - Frontend to Ollama: Direct HTTP `fetch` calls over localhost for streaming endpoints:
     * `POST http://localhost:11434/api/pull`: Consumes NDJSON byte progress stream.
     * `POST http://localhost:11434/api/generate`: Issues structured review prompts with `format: "json"`.

4. Data Sources and Destinations:
   - Source Code Content: Authored in Monaco Editor -> Cached in `localStorage` (`waypoint_project_files`) -> Written temporarily to `std::env::temp_dir().join("waypoint_runner")` during compilation -> Destroyed/Overwritten on subsequent runs.
   - Compiler Output: Produced by GCC/G++/Javac/Python -> Captured via standard process pipes -> Sanitized in Rust and TypeScript -> Rendered in React Output Panel.
   - Review Context: Student problem statement + active file code -> Bundled into LLM prompt -> Evaluated by Ollama model -> JSON response rendered in Review Console.

6. Important Architectural Decisions:
   - Decision 1 (Tauri over Electron): Tauri was selected to eliminate Chromium bloat, reducing base installer size from ~120 MB to 6.3 MB, and operational RAM footprint from ~800 MB to ~45 MB.
   - Decision 2 (Vanilla CSS over Frameworks): The team instituted a strict constraint prohibiting Tailwind CSS or component libraries to achieve an authentic, lightweight Sand / Editorial design system using custom CSS properties with zero runtime styling overhead.
   - Decision 3 (Localhost Process Execution vs Docker Containerization): Because university lab machines frequently lack hardware virtualization support or administrator rights required for Docker Desktop, Waypoint compiles directly via native host toolchains with path sanitization.
   - Decision 4 (Dual Review Engine): If Ollama is offline or times out (3.5s limit), `ReviewService` gracefully falls back to `AstAnalysisService`, ensuring students always receive feedback even on air-gapped lab PCs without AI models.

7. Existing Architectural Limitations:
   - Files are stored in browser `localStorage` and compiled via an OS temporary directory rather than maintaining direct two-way binding with arbitrary native disk directories.
   - Terminal emulator runs child processes via `cmd /C` rather than implementing a full pseudo-terminal (PTY) interface with ANSI color escape code handling.

   - Step 7 (Improvement & Iteration): The student copies or manually applies the suggestion, edits the file, runs it again to ensure tests pass, and clicks "Review" to verify if the code has reached optimal state.

SECTION G — TECHNICAL WORKFLOW
================================================================================

1. Technical Execution Pipeline:
   - Phase 1 (Input Acquisition): React collects active file name, code content string, and optional stdin input. Dispatches Tauri IPC call `compile_and_run_file`.
   - Phase 2 (Disk Staging): Rust `compile_and_run_file` determines target extension, resolves `%TEMP%\waypoint_runner`, creates the directory if missing, and writes the source file to disk.
   - Phase 3 (Compilation & Toolchain Invocation):
     * C++: Executes `g++ -std=c++17 <filename> -o program.exe` without creating a console window.
     * C: Executes `gcc <filename> -o program.exe`.
     * Java: Executes `javac <filename>`, followed by `java -cp . <classname>`.
     * Python: Skips compilation; directly launches `python -u <filename>`.
   - Phase 4 (Process Piping & Timing): Rust measures execution start/end time. If stdin bytes exist, writes them to `child.stdin`. Waits for process exit.
   - Phase 5 (Diagnostic Sanitization): Rust cleans raw stderr:
     * Replaces `%TEMP%\waypoint_runner\` paths with clean relative filenames.
     * Matches linker errors (`undefined reference to WinMain` or `main`) and replaces them with an educational notice explaining that every C/C++ program requires an `int main()` entry point.
   - Phase 6 (Output Dispatch): Returns structured `CommandOutput` struct `{ success, stdout, stderr, exit_code }` across IPC to React.

2. Error Diagnostics & Navigation Pipeline:
   - React `ExecutionService.runProgram` receives stderr.
   - Regex engines extract line numbers:
     * Python: `/File\s+["'][^"']+["'],\s+line\s+(\d+)/i`
     * GCC/Clang: `/([^\s:]+):(\d+):(\d+):\s*(?:fatal\s+)?error:\s*(.*)/i`
     * Java: `/([^\s:]+):(\d+):\s*error:\s*(.*)/i`
   - Strips deep system paths (MinGW `ld.exe`, `crtexe.c`).
   - If line number is found, sets `errorLocation`. Monaco Editor triggers `editor.revealLineInCenter(errorLine)` and paints a custom CSS glyph decoration (`monaco-error-line-highlight`).

3. Local AI Review Pipeline:
   - User triggers review -> `ReviewService.requestSingleIssueReview(file)` initiates.
   - Verification Step: Sends HTTP GET with 2000ms timeout to `http://localhost:11434/api/tags`.
   - If Ollama is running:
     * Injects System Prompt enforcing:
       1) Combine Problem Statement with code context.
       2) Never rewrite the whole file.
       3) Identify only the single highest-priority optimization / Big-O bottleneck.
       4) Return strictly JSON format `{ isOptimal, title, category, severity, explanation, benefit, originalCode, suggestedCode }`.
     * Dispatches `POST http://localhost:11434/api/generate` with `format: "json"` and a 3500ms timeout.
     * Parses JSON response. If `isOptimal === true`, displays completion badge. Otherwise, populates finding card.
   - Fallback Step: If Ollama is unreachable or times out, seamlessly routes to `AstAnalysisService.analyzeCode(file)`. Evaluates deterministic heuristic catalog across C++, Python, Java, and C. Returns matching rule finding or confirms optimal state.

SECTION P — RISKS, CHALLENGES, AND LIMITATIONS
================================================================================

1. Observed Limitations in Current Codebase:
   - Virtual Storage Boundary: Project Explorer persists file trees in browser `localStorage`. Native OS file system directory binding is not yet complete.
   - Infinite Loop Vulnerability: Programs containing unintentional infinite loops (`while(true)`) will run indefinitely until the user manually switches tabs or kills the task via terminal.
   - Regex Heuristic Parsing: Error extraction and deterministic review rules rely on regular expressions, which can fail on unconventional or heavily nested code structures.
   - Windows Privilege Boundary: Running `winget` from the Setup Wizard requires standard administrative elevation on Windows PCs.

2. Potential Technical & External Risks:
   - Hardware Variance in University Labs: Older lab PCs with 4GB RAM may struggle to run Ollama 3B models alongside the operating system.
     * Mitigation Strategy: Waypoint sets the ultra-lightweight Qwen 2.5 Coder 1.5B (0.98 GB) as default, and provides instant fallback to the zero-RAM `AstAnalysisService`.
   - Missing System Compilers: If MinGW or JDK is absent and the student lacks admin privileges to install via `winget`, compilation will fail.
     * Mitigation Strategy: The Setup Wizard clearly highlights missing compilers and provides direct manual download instructions.

3. Security & Safety Considerations:
   - Waypoint runs native compilers directly on the student machine. It does not implement full hypervisor or container sandbox isolation.
   - Code executes with the permissions of the current logged-in user.
